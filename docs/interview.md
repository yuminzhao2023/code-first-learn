# 面试讲解提纲

## 值得展示的工程决策

- 步骤对齐按类型、名称与出现顺序配对，保持稳定顺序，不把缺失步骤当作零耗时，不推断真实调用关系。
- 异常统计以失败 Trace 为来源，同一执行去重；重复事件保留最新记录，并明确并列排序规则。
- Trace 深链接与本地搜索、筛选和分页保持一致，刷新和浏览器前进后退有行为测试覆盖。
- 搜索选择器通过 Portal 避免 Card 裁剪，处理视口边界、键盘导航和监听清理。
- 截图测试统一系统、浏览器和字体环境，并拆分共享导航与页面内容；行为测试补充截图无法发现的业务回归。

## 视觉验证的环境差异

开发过程中曾出现 macOS 本机截图通过、Windows 环境截图不同的情况。仓库因此增加固定 Linux Playwright 容器及 CI 视觉任务，以减少系统、字体和浏览器差异。

本地 Docker 便于修改后即时对比，但需要额外安装和硬件资源；CI 统一环境便于协作，但需要等待工作流并查看失败产物。无 Docker 的笔记本可以运行本机行为测试，统一视觉对比仍保留待验证状态。不能把本机行为通过描述成视觉批准。

## 当前能力边界

项目能够展示 React / TypeScript 状态设计、领域逻辑、可访问交互和回归验证。它不证明真实 AI 产品运行链路、生产可观测性或大数据性能：当前没有模型调用、流式输出、工具执行、后端或生产数据。

整体 P95 缺少原始请求或可合并分布，因此不展示虚构聚合值。这个取舍可用于解释数据口径如何约束 UI。

面试时优先讲清规则、测试证据与限制；演示前确认当前提交的 CI、截图审核和部署结果，不将计划描述为已完成能力。
