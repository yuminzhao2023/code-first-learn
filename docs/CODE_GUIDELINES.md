# 代码规范

## 1. 模块组织与依赖

- 按职责划分模块，保持同类模块的组织方式一致。
- 关系紧密、共同修改的代码和资源放在一起；公共能力由明确的共享模块维护。
- 模块应提供清晰的接口，调用方通过接口使用能力，避免依赖内部实现。
- 保持依赖方向清晰，避免循环依赖；通用模块不依赖具体业务页面。
- 调整模块边界时，同步更新引用、测试和相关文档。

## 2. 职责划分与复用

- 组件负责视图与交互，复杂业务计算从渲染逻辑中分离，以便独立理解和验证。
- 业务计算优先通过显式输入返回结果；数据访问和其他副作用集中在职责明确的位置。
- 避免修改调用方传入的数据。确需修改时，应在接口契约中明确说明。
- 抽取共享能力时确认使用场景和行为契约一致，保持接口简洁。
- 拆分应降低理解和修改成本，避免过度拆分或为尚未出现的需求增加抽象。

## 3. 类型、数据与状态

- 使用明确的类型表达数据契约，避免用 `any` 或类型断言掩盖不确定性。
- 在外部数据进入系统的边界进行校验，明确缺失、无效和失败情况的处理方式。
- 同一信息保持明确的权威来源；能够从已有数据计算出的值，优先派生而非重复存储。
- 状态应由合适的组件或模块持有，避免多个位置独立维护同一状态。
- 副作用应有明确的触发条件，并在需要时处理清理、取消和重复执行。

## 4. 命名、格式与样式

- 名称表达用途和业务含义，遵循所在模块已有的命名约定。
- 函数、组件和文件保持职责集中；复杂表达式可通过局部变量或辅助函数分步表达。
- 多层 JSX、多步骤函数和样式规则应使用清晰的换行与缩进，便于检查层级和控制流。
- 样式按作用范围组织：局部样式随所属模块维护，全局样式和设计令牌集中管理。
- 限制样式选择器的影响范围，避免局部修改意外影响其他模块。

## 5. 注释与接口说明

代码应首先通过命名、类型和结构表达意图。以下信息无法直接从代码看出时，需要在相关实现附近说明：

- 业务规则、边界条件和必须保持的不变量。
- 数据格式、单位、来源及其他影响正确性的假设。
- 特殊算法、实现取舍及其原因。
- 状态同步、副作用和资源生命周期中的约束。
- 兼容处理或临时方案的原因、适用条件与移除条件；有相关 issue 时附引用。

对供其他模块使用且行为不直观的接口，使用 JSDoc 说明输入约束、返回语义、错误行为和副作用。无需重复类型已经表达的信息。

注释随实现同步维护，重点解释原因与约束。避免逐行复述代码、无意义的文件头和已经过时的说明。详细需求与设计决策保留在对应文档中，必要时从代码引用。

## 6. 文档组织与引用

- 规范文档放在 `docs/` 根目录，组件与功能说明放在对应子目录。每项规则只在一处维护；其他文档仅在具体步骤需要该规则时引用，不复制全文或重复列出规范目录。
- AGENTS 维护 AI 的必读入口；规范文档不再要求返回阅读 AGENTS，也不在末尾添加通用“相关规范”列表。
- 规范之间的阅读要求保持单向，执行依赖必须使用明确的 Markdown 链接，不用普通文字或行内代码代替。新增引用前确认目标提供当前步骤缺少的规则，并检查是否经其他规范返回当前文件；已有上下文无需再次要求加载。
- README 承担面向人的导航，可列出规范和组件文档。普通导航、来源或示例链接不等于必读要求，不应沿全部链接递归阅读。
- 组件与功能文档按任务查阅；保留指向类型、实现和具体示例的有效链接，不把整个文档目录变成必读清单。
- 仓库内使用相对链接；同一规范文档不重复链接同一文件，必要时用普通文字指代已引用的规范。
- 新增、迁移或修改 Markdown 后运行 `npm run docs:check`。该命令按实际使用的 Markdown 链接检查本地目标、规范的重复文件链接、规范回指入口的链接和规范链接环；图片仅检查本地目标是否存在。普通导航与示例不属于执行依赖，但规范之间的直接文档链接统一按依赖检查，应避免用这类链接表达纯导航。

- 检查器使用 CommonMark 解析，不检查代码示例、未使用的引用定义、原始 HTML、锚点与外链可用性；不理解自然语言阅读要求，也不能判断引用是否必要。更改检查器后运行 `npm run test:docs`，普通文字中的阅读要求与引用必要性仍需人工审阅。

## 7. 变更与评审

- 将改动限制在任务所需范围，避免混入无关重构或全文件格式调整。
- 修改行为时同步检查调用方、测试和文档，验证正常流程与相关边界情况。
- 新增依赖应有明确用途，并与项目运行环境兼容。
- 评审同时关注正确性、可读性、模块边界和验证证据；注释不能替代清晰的实现或必要的测试。
